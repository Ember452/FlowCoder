## 一、使用说明

1. 简历主体优先用「标准版」；版面紧张用「精简版」；作品集或面试自我介绍用「详细版」。
2. 每条经历遵循"动词开头 + 做什么 + 怎么做 + 成果/指标"的结构，避免只堆名词。
3. 业务价值量化（token 成本下降 %、耗时缩短 %、拦截覆盖率 % 等）必须按《量化测试方法》实测取得真实数据后填入，不得编造；未实测的项目改为定性表述或删除该收益句。
4. 技术关键词用于通过 ATS（简历解析系统）筛选，须与 JD（岗位描述）高频词对齐。
5. 面试前务必过一遍「面试深挖问答」，确保每条简历陈述都能展开讲清底层实现，否则宁可删掉该条。

## 四、详细版（5–7 条，约 650 字，作品集 / 面试深挖用）

**FlowCoder —— 本地优先的 AI Agent 运行时**　`独立开发`　`2026.06 – 2026.08`
`Python 3.11` `Pydantic` `asyncio` `Starlette` `Uvicorn` `Textual` `WebSocket` `MCP` `A2A` `Vue 3`

**项目背景**：FlowCoder 是一个本地优先的 AI 编码助手运行时，围绕 Agent 核心循环、工具治理、上下文工程、长期记忆与多 Agent 协作五大能力构建，目标是提供一个可本地部署、行为可控、可插件化扩展的类 Claude Code Agent 系统。

- **Agent 核心循环与事件流抽象**：设计 ReAct 推理-行动主循环，将模型流式输出、工具调用、结果回灌、多轮收敛统一抽象为 AgentEvent 事件流；循环内集成中断恢复、响应历史回放与工具授权挂起/继续机制，使权限审批与用户提问可异步挂起再恢复执行。
- **多协议 LLM 适配层**：在 client 层抽象统一调用接口，providers 层分别实现 Anthropic Messages、OpenAI Responses、OpenAI Compatible 三种协议的请求构造与流式 SSE 解析，新增供应商只需实现 provider 接口，无需改动 Agent 循环。
- **工具系统与并发调度**：基于 Pydantic 模型自动生成工具 JSON Schema，内置 read/write/edit/glob/grep/bash/子 Agent/团队任务/worktree 等 20+ 工具；按 read/write/command 副作用边界划分工具类别，只读工具可并发执行，写操作与命令执行经权限审批拦截，降低串行等待。
- **双层上下文压缩与记忆系统**：Layer1 对大体积工具结果做落盘替换与预算裁剪，Layer2 在临近窗口上限时触发自动 compact 生成摘要并重建历史；MemoryHub 统一管理长期记忆，支持 Markdown、TencentDB Agent Memory 与自定义 Python Memory Provider，按 work_dir 隔离项目记忆并在循环中周期性提取与注入。
- **权限治理与扩展机制**：实现 6 种权限模式矩阵（default/acceptEdits/plan/bypassPermissions/custom/dontAsk），配合规则引擎、路径沙箱、危险命令识别与 Hooks 钩子引擎做执行前拦截与执行后回调；通过 Skills 声明式加载与 MCP 协议集成扩展工具能力，使 Agent 行为可控且可插件化扩展。
- **多 Agent 协作与任务隔离**：通过 mailbox 通信、后台任务、子 Agent 委派与 git worktree 支持并行任务处理、状态追踪与实验性改动隔离，多进程 spawn 支持独立工作目录的子任务执行。
- **三态一体运行形态与工程化**：基于 Starlette + Uvicorn 实现 daemon（HTTP 控制面建会话/发任务/回权限，WebSocket 数据面推 StreamText/ToolUse/LoopComplete 事件），配 Textual TUI 与 headless CLI，并以 Vue 3 Web UI 实时渲染流式输出、工具调用与权限弹窗；项目采用 src layout 分层架构，测试按 unit/integration/e2e 三层分层覆盖 96 个文件，CI 流水线集成 lint 与分层测试。

## 七、面试深挖问答准备

简历每一条都可能被追问实现细节，以下给出高频追问与答题方向，面试前务必逐条能口述。

**Q1：Agent 核心循环是怎么转的？工具调用结果怎么回到下一轮？**
答方向：ReAct 循环——准备上下文 → 调用 LLM 流式接口 → 解析 StreamText 与 ToolUse 事件 → 执行工具拿 ToolResult → 把 assistant/tool_use/tool_result 追加到 conversation.history → 进入下一轮，直到模型不再发起工具调用即 LoopComplete。强调统一事件流抽象与 history 追加接续。

**Q2：三种模型协议怎么统一？新增一个供应商要改哪里？**
答方向：client 层定义统一调用接口（stream/messages），providers 层为每种协议实现请求构造与 SSE 解析，把协议差异收敛在 provider 内；Agent 循环只依赖统一接口。新增供应商只需实现 provider 接口并注册，不动循环。

**Q3：双层上下文压缩分别解决什么？**
答方向：Layer1 解决单次工具结果过大（如读大文件、grep 海量命中）——落盘替换 + 预算裁剪，避免单条消息撑爆窗口；Layer2 解决多轮累积超限——在临近上限时自动 compact 生成摘要并 replace_history，有损但保住长对话连续性。

**Q4：6 种权限模式怎么落地？只读并发怎么保证安全？**
答方向：权限模式是 (mode × tool_category) 的决策矩阵，输出 allow/deny/ask；只读工具（read 类）无副作用可并发，写操作与命令（command）必须经授权（ask）或被规则/沙箱拦截。沙箱以 work_dir 为根做路径越界校验。

**Q5：daemon 的 HTTP 和 WebSocket 怎么分工？**
答方向：HTTP 是控制面——建会话、发任务、回权限、改配置，一问一答；WebSocket 是数据面——订阅某 session 的事件日志，实时推 StreamText/ToolUse/PermissionRequest/LoopComplete，支持历史回放。多轮上下文靠复用同一 session 的 ConversationManager 追加消息接续。

**Q6：MemoryHub 怎么做插件化？**
答方向：定义 Memory Provider 接口，内置 Markdown（文件落盘）、TencentDB Agent Memory、自定义 Python Provider 三种实现；按 work_dir 隔离项目记忆，循环开始时 load 注入、周期性 extract 提取，compact 后可重新注入。

**Q7：项目里最难的一个问题是什么？**
答方向（任选其一，须能讲清）：① 权限/提问的异步挂起与恢复——用 asyncio.Future 把 PermissionRequest 挂起，前端回传决策后 resolve_future 让工具继续；② 双层压缩的有损边界——什么时机触发 compact、哪些历史可丢哪些必须保留；③ 多协议流式解析差异——三种协议 SSE 事件结构不同，统一收敛到 AgentEvent。

## 八、写法注意事项

1. **不夸大角色**：作为个人项目写"独立设计并实现"是准确的；若面试中某模块实现细节讲不清，宁可在简历中降级表述（如"参与设计"）或删掉该条，避免被追问穿。
2. **量化必须实测**：所有"下降 XX%""缩短 XX%"类数据必须来自《量化测试方法》文档的实测结果，不得编造；跑不出显著差异的特性如实降级为定性表述（如写"支持只读并发"而非"耗时下降 XX%"），宁缺毋假。第六节结构性指标（20+ 工具、6 模式、3 协议等）可不经测试直接引用，因均可在仓库核查。
3. **技术词要对齐 JD**：投递前把 JD 高频词（如"Agent""工具调用""流式""上下文""RAG""MCP"）与第五节关键词对齐，适当调整表述顺序。
4. **避免空泛名词堆砌**：每条经历至少有一句"怎么做"的实现描述（用什么技术/什么机制），不能只列"使用了 asyncio、Pydantic"。
5. **诚实边界**：FlowCoder 是在已有开源实现基础上做的深度二次开发与工程化重构，面试被问"哪些是从零写的"时，应诚实区分"自己实现/自己重构/直接复用"三部分，重点讲自己做的工程化决策与改动理由，比把全部说成从零写更可信。
6. **准备可演示产物**：面试前确保本地能跑通 `flowcoder-daemon` + Web UI 实时对话，作为可演示佐证，比纯口述更有说服力。
