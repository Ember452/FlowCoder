# ADR：自动化能力产品接线（P5.5 收尾）

- 状态：Accepted
- 日期：2026-08-29
- 关联：docs/specs/ 三篇 P5 ADR、docs/architecture/config.md、daemon.md

## 背景

P5a/P5b/P3 交付了 scheduler / watchdog / budget 三个能力包，但验收语义是
"库就绪 + 集成点就绪"——daemon/app 的启动路径零引用（P5.5 之前 grep 可证）。
本阶段补上最后一公里：配置入口 + 启动装配 + 预算注入，使三件事成为
"配置即用"的产品能力。

## 决策与理由

### D1：默认全关，零配置零变化

三个新配置段（`scheduler` / `watchdog` / `budget`）缺省时：
- 不创建任何后台任务（无调度器状态文件、无看门狗状态文件）；
- Agent 构造不注入预算（`_budget_state is None`）。

"零配置零变化"是独立测试断言（test_p55_wiring.py），不是口头承诺——
这是对 P1c"默认 off"模式的复用：能力出厂即装、开关在用户手里。

### D2：装配集中在 daemon/background.py，绕开 app.py 禁令

后台服务的起停（lifespan）只动 `daemon/server.py` 的 lifespan 构造一处；
全部装配逻辑（构建 Scheduler/Watchdog、读配置、选信号源）集中在
`daemon/background.py`。理由：
- app.py 是 god file（R3 待清算），AGENTS.md 明令禁止加逻辑；
- server_state 是状态门面，不承担装配；
- background.py 与 R3 的 bootstrap 方向一致，R3 拆 app.py 时装配可整体迁入。

### D3：watchdog/scheduler 的 daemon 适配器分置两侧

`watchdog_job.py`（送达适配）放在 daemon 包而非 watchdog 包——与
`scheduler/daemon_job.py` 同构：能力包保持零上层依赖（依赖方向），
daemon 专属的"提醒变成 Agent 回合"翻译在 daemon 侧完成。

### D4：预算闸的接线范围——daemon/CLI/eval 全覆盖，TUI 延后

`create_agent_from_config`（daemon/CLI/eval 共用）按 `config.budget`
构造 Budget 注入 Agent。TUI 的 Agent 在 app.py 自建（god file），
接线随 R3 app.py 清算一并处理——为此在 R3 的拆分清单里登记。
配置校验复用 Budget 自身语义（至少一项上限、成本需配单价），
在配置加载期即报错（与 cron 在配置期校验同理）。

### D5：cron 在配置期校验

`scheduler.jobs[].cron` 在 `load_config` 时用 CronExpr 解析校验——
写错 cron 在启动时得到明确报错，而不是等到第一次触发才发现
（静默不触发的定时任务是最难排查的故障）。

## 配置示例

```yaml
scheduler:
  enabled: true
  jobs:
    - name: nightly
      cron: "0 2 * * *"
      prompt: "夜间依赖巡检，产出简要报告"

watchdog:
  enabled: true
  poll_interval_s: 300
  watch_git: true
  paths: ["src/"]

budget:
  max_turns: 50
  max_seconds: 1800
```

## 交付物

- `config`：SchedulerConfig / WatchdogConfig / BudgetConfig + 三段校验
  （cron 配置期校验、budget 语义复用）+ 多层合并 + declared 标记
- `daemon/background.py`：lifespan 装配（调度器/看门狗/Outbox 清理三任务）
- `daemon/watchdog_job.py`：送达适配（提醒 → Agent 回合）
- `agent/factory.py`：按 config.budget 注入预算
